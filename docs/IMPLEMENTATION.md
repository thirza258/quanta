## Modeling conventions

- All default prices and factor observations are explicitly synthetic. Names such as “1929-inspired” describe stress mechanisms, not fitted historical reconstructions.
- Research-lab OHLCV uses a weekday-only synthetic calendar and 252 observations per modeled year. Its backtester does not model intraday execution. The new terminal separately models weekday minute-bar sessions under its documented cash execution profile.
- Signals from a close act at the **next open**. Entries commit available cash after fees; exits deduct fees and slippage. The final position is marked to the last close and is not forcibly liquidated.
- The benchmark is buy-and-hold of the same supplied path, including entry fees/slippage. It is not labeled the S&P 500.
- Maximum drawdown includes initial capital. Win rate and profit factor use closed round trips. Profit factor is undefined when there are no gross losses; undefined values are `null`, never infinity in JSON.
- Sharpe and Sortino use a 3% annual risk-free rate. Alpha and beta are a descriptive single-factor comparison against the same-path benchmark. Annualized arithmetic alpha and geometric CAGR are different quantities.
- VaR/CVaR are nonnegative daily loss magnitudes at 95%; they are estimates, not maximum-loss guarantees.
- AMM IL compares a fee-free LP position with holding its initial inventory. Concentrated liquidity uses piecewise inventories clamped to range boundaries. Swap output separately includes the swap fee.
- Regression examples plant known exposures in synthetic data. The ridge comparison trains on the first 75% only, including its scaler. Portfolio optimization uses a fixed 10% diagonal covariance shrinkage; this is not represented as estimated Ledoit–Wolf shrinkage.
- The research lab’s original paper-broker calculator remains stateless. The new `/simulator` terminal uses a separate server-owned ledger with transactional reservations, fills, costs, version checks, idempotency, archived resets, and account recovery. See [its execution and persistence conventions](SIMULATOR.md).
- Lesson valuation arithmetic and its accompanying price strategy are distinct exercises. Synthetic trend returns do not validate NCAV/Graham selection performance.

## Persistence and recovery

Guest learning data remains in a versioned browser-storage namespace. Simulator guest previews instead use a separate signed browser cookie and server-backed trading state, as detailed in the simulator guide. Registering copies guest progress into a new account. Signing in loads that account’s remote state. Local pending edits include their base server revision. A same-revision reconnect retries them; a divergent revision preserves the local copy and stops sync instead of silently overwriting either version. Export the local workspace from the profile menu before resolving conflicting versions. Resolve sync conflict → Use account copy explicitly replaces local edits with the latest server copy after confirmation. Passwords and JWTs are never stored in browser storage.

Workspace snapshots store code, parameters, summary metrics, notes, and progress. Full time series are recreated by rerunning the saved seed/configuration. API snapshots are limited to 1.2 MB; local exports provide an escape hatch when retaining many experiments.

## Beginner entry and assessment progression

The ordered catalog now starts with `trading-fundamentals` (displayed as “Start here”), followed by the original six tracks and the dedicated stock-ML track. Its IDs `0.1`–`0.8` preserve existing IDs and stored progress. New workspaces start at `0.1`; existing last-lesson pointers are retained. Beginner lessons initially load reading view; the sandbox is loaded on demand.

Practice uses the existing submission route with an optional zero-based `question` index. Question zero retains the original workspace key. Subsequent questions use `lessonId:q2`, `lessonId:q3`, and so on. Completing a beginner module requires all three practice answers to have passed.

A course's progress denominator includes modules and exams, with equal weight per completed item. A pass for the current exam version remains valid after a failed retake. Exam access and later tracks are open so learners may use them as readiness checks. Exams have no enforced time limit. The displayed duration is an estimate, and the required answer count uses the ceiling of the percentage threshold.

`ExamSubmission` is an additive SQLModel table created during normal API initialization for SQLite or PostgreSQL. Authenticated submissions are graded from the server catalog, stored by account, and deduplicated by attempt UUID. Reusing a UUID with another account, exam, version, or answers fails. Invalid or incomplete answers fail validation. Guest online results and device grading remain in workspace storage; offline scores retain their provenance when later synced.

Exam history in a workspace keeps at most 20 results per exam, retaining the best current-version attempt. The authenticated history endpoint returns the latest 50 online submissions. Missing results can be merged into the workspace without rewriting an identical snapshot. Exam versions protect against resuming incompatible drafts. This is a self-study system whose catalog intentionally exposes answer keys; it does not claim academic integrity guarantees against a learner editing their own workspace.

History recovery also reconciles a draft with an already-recorded submission after a lost response. Matching identifiers, versions, and answers retire the draft automatically. Later answer edits remain saved until the learner explicitly carries them into a new attempt or discards them to review the recorded result. A conflicting submission refreshes account history so the learner can recover without reloading; the original submission remains immutable.
